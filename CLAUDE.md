# public-ui.github.io

Docusaurus v3 documentation site for the KoliBri web component library (`@public-ui/*`). German is the default locale, English translations live in `i18n/en/docusaurus-plugin-content-docs/current/`.

## Commands

- Package manager is **pnpm** (`pnpm install`). The postinstall copies assets from `@public-ui/*` into `static/assets`.
- `pnpm run startonly` starts the dev server on http://localhost:3000 without regenerating the API readmes; `npm start` runs `gen:doc` first.
- `pnpm run lint` = `tsc` + ESLint on `src` + `scripts/check.preview.context.js`. MDX is covered by neither `tsc` nor ESLint – the context check is the only automated MDX check, so also open changed pages in the dev server.
- `pnpm run format` checks Prettier for `blog`, `docs`, `src`.
- `pnpm run build` is slow (several minutes). Run it before merging, not for every edit.
- `readmes/` is generated from `node_modules/@public-ui/components/doc` by `gen:doc` and is git-ignored. It reflects the **installed** KoliBri version – after bumping `@public-ui/*` in `package.json`, run `pnpm install` and `pnpm run gen:doc`.

## Conventions

- Conventional Commits (enforced by commitlint).
- Prettier: 120 characters, single quotes, tabs. `.md` files use spaces (`.editorconfig`).
- File names in English (they become the URL). No `slug` in frontmatter (only `docs/00-welcome.mdx` has one), no `tags`.
- Translations: use the `translate()` function, not the `<Translate>` component. Keys are English kebab-case, the default `message` is German. No custom descriptions.
- Doc prose is German with correct umlauts; code, property names and technical terms stay English. Write property names in camelCase (`_hideMsg`, not `_hide-msg`).

## Component documentation (`docs/30-components/`)

### Page structure

`input-number.mdx` is the blueprint for all form components. Keep this order:

`# Name` → **Synonyme** → **Beschreibung** (including the native HTML element it is based on) → `## Beispiel` → `## Barrierefreiheit` (bullets) → `### Konkrete Designentscheidungen` (table) → `### Links und Referenzen` → `## Verwendung` → `### Tastatursteuerung` → `### Best Practices / Empfehlungen` → `### Anwendungsfälle` → `### FAQ` → `## Playground` → `## Funktionalitäten` (one `###` per feature with its own preview) → `## API` → `### Events` → `<Readme />`.

### Previews

Every `<XyzPreview>` needs a `context` matching its section; presentation is derived from `PREVIEW_CONTEXT_CONFIG` in `src/components/previews/Preview.tsx`.

| Section               | `context`      | Properties offered       |
| --------------------- | -------------- | ------------------------ |
| `## Beispiel`         | `"example"`    | none                     |
| `## Playground`       | `"playground"` | all sensible ones        |
| `## Funktionalitäten` | `"feature"`    | only `visibleProperties` |

- `visibleProperties` is required for `context="feature"` and may only contain keys defined in the preview's `propertyComponents`. Add a missing control to the preview (e.g. `_touched: <BooleanProperty label="Touched" />`) if the component supports the property.
- Examples must show the feature immediately – set `initialProps` (e.g. `_value`) instead of telling the reader to type or select something first. Previews that keep `_value` in internal state must initialise it from `props.initialProps?._value` (see `Textarea.tsx`, `Combobox.tsx`).
- A basic example must be meaningful on its own (a Combobox needs `_suggestions`, a Radio or Select needs `_options`).

### Shared snippets (`_shared/`)

Text repeated across pages lives once as MDX in `docs/30-components/_shared/` and is imported (`import LabelNote from './_shared/a11y-properties/label.md';`). The leading underscore keeps Docusaurus from routing the snippets or listing them in the autogenerated sidebar.

- `a11y-properties/` – single bullets for "Barrierefreiheit", used as `* <LabelNote />`
- `features/` – complete feature sections for "Funktionalitäten"
- `feature-properties/` – single property bullets (`- <DisabledProp />`) for properties not every component has
- `keyboard/`, `api/` – keyboard intros/notes and the events intro

Use a snippet only if it is accurate for the component; otherwise write local text. Change the snippet instead of copying and adapting it. Delete snippets that are no longer imported. Snippets must not contain headings (they don't show up in the TOC).

### Content rules

These come from review feedback on the form components:

- **"Barrierefreiheit" explains what KoliBri adds on top of the native element, which decisions were made, and which accessibility recommendations follow.** Ask: does a developer or accessibility tester gain anything from this?
- **No implementation details** there – no ARIA roles/attributes, `tabindex`, hidden elements, CSS tricks or internal mechanics. Describe what users and screen readers observably experience instead. The implementation is visible in the source.
- **No duplication**: if something is already in "Konkrete Designentscheidungen", it doesn't need a bullet as well.
- **Features belong in "Funktionalitäten"** (clear button, visibility toggle, file selection, variants …), including their accessibility-relevant behaviour, not as an accessibility bullet.
- **General recommendations belong in "Best Practices / Empfehlungen"** (e.g. validating values in the application).
- **Rationales must be backed**: every "Begründung", "bewusst", "um … zu" needs evidence in the KoliBri source (code comments, JSDoc) or its git history. Otherwise remove the motive and keep only observable facts – don't invent reasons.

### Verifying against KoliBri

Check behaviour against the KoliBri source at the version pinned in `package.json` (repo `public-ui/kolibri`, tag e.g. `4.4.0`, path `packages/components/src`), not against old docs or the readmes alone. Readme/JSDoc texts can be outdated (e.g. `_hideMsg` claims the message stays in the DOM; it is removed entirely). Link known KoliBri bugs as a note next to the affected feature, not under "Barrierefreiheit".
